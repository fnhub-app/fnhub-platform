# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## ⛔ HARD RULE — never hardcode "CLFN" / "Constance Lake" in new code
This is a multi-tenant product that **may be sold to other First Nations**, so nation identity must always come from configuration, never from literals. In any code you write or touch:
- **Do NOT** write `"CLFN"`, `"Constance Lake First Nation"`, the CLFN logo, CLFN colors/hex, CLFN email domains, or any other CLFN-specific string as a literal.
- **DO** read nation identity from config: `NATION_CONFIG.display_name` / `NATION_CONFIG.short` / `NATION_CONFIG.primary_color` (theme), the saved theme (`_appSettings.theme`, applied via `_applyTheme`), and the per-nation registry in `shared-config.js` (`NATIONS_DIRECTORY` / `resolveNation()`). If a needed value isn't in config yet, **add a config field** rather than a literal.
- The `CLFN_*` *identifier prefixes* on existing globals (`CLFN_MODULES`, `CLFN_AUTH`, `CLFN_PERMS`, `CLFN_CONFIG_LOADED`, etc.) are **fine to keep using** — they're internal names, not user-facing nation references. The rule is about **user-facing/branding values and behavior**, not these symbol names.
- There is a large backlog of existing hardcoded CLFN strings (noted throughout this file). **We will clean those up in a dedicated pass later** — do not let existing literals justify adding new ones. Leave existing ones unless the task is specifically that cleanup.

## Working agreement — commits & pushes
**Always ask for explicit confirmation before committing or pushing.** Make the changes and summarize what changed, then wait for the user's go-ahead — do not auto-commit or auto-push, even when a task looks complete. This applies to every branch (including `main`).

## Project Overview

Multi-tenant SaaS housing management platform for First Nations. First customer is **Constance Lake First Nation (CLFN)**; the architecture is being prepared to onboard additional nations (database-per-nation, subdomain-per-nation, per-nation module licensing). Superuser admin tooling lives in a **separate codebase** and is out of scope here.

The active roadmap and phase status (A0/A/B/C/D/E + F1/F2/F3/F3B for the Finance module) are tracked in `PLAN.md` — read it before starting non-trivial work to know what's locked, in-progress, or deferred.

## Build / Run / Deploy

- **No build step, no package manager, no test runner.** This is a static-files SPA: vanilla JS (no framework), plain CSS, served as-is.
- **Local dev:** open the HTML files directly or serve the project root with any static server (e.g. `python -m http.server`, `npx serve .`). All inter-page navigation is `window.location.href` to other `.html` files in the same directory.
- **Deploy:** Cloudflare Workers (static assets) via the workflow in `.github/workflows/deploy-cloudflare.yml` — every push to `main` deploys the repo root (`wrangler.jsonc`, `assets.directory: "."`). `.assetsignore` keeps non-public files (`.git`, `supabase`, `docs`, `*.md`, `*.sql`, `admin/`, the wrangler configs) out of the deploy. Response headers (incl. CSP) come from `_headers`. Live at `clfn.fnhub.app` (nation subdomain of `fnhub.app`). The admin control panel deploys separately (`wrangler.admin.jsonc` → `admin.fnhub.app`). **Azure Static Web Apps has been decommissioned** — the old `staticwebapp.config.json` and its deploy workflow were removed.
- **Backend:** Supabase project `fkhzrbalumzeripzolph` (URL + anon key hardcoded in `shared-config.js`). Auth, staff lookup, applications, units, audit, finance tables — all REST/PostgREST calls from the browser. There is no API server in this repo.
- **Schema changes:** SQL migrations are run by the user via the Supabase SQL Editor (not via this repo). Phase F2 in `PLAN.md` documents the finance schema that's already deployed.
- **Edge Functions:** Source lives under `supabase/functions/`. Deployed manually via the Supabase Dashboard (paste into the function editor) or via `supabase functions deploy <name>` (CLI install on Windows is via Scoop, not npm — `npm i -g supabase` is explicitly blocked). ## Architecture

### Page model
Each top-level feature is a separate HTML file that the user navigates between via full page loads:

- `index.html` — sign-in screen and post-login employee landing
- `housing.html` — Applications & Worklist, Dashboard, Settings (the main hub)
- `inventory.html`, `tenants.html`, `match.html` — housing inventory views
- `renos.html` — Renovations / SOWs / Progress / Reno Approvals
- `contractors.html` — contractor registry (auto-enabled when Renovations is on)
- `finance.html` — Finance module (rent ledger, loans, invoices, arrangements, collections, journal, hydro/gas — see Phase F1–F3 in `PLAN.md`)

Auth state crosses page loads via `sessionStorage` (`HOUSING_SESSION` is stashed by `housing.html` and rehydrated by sub-pages). On any page load the boot sequence resolves the role from the Supabase `staff` table via `resolveHousingRole()`.

### Shared layer (loaded by every page in this order)
```
shared.js  →  shared-config.js  →  shared-auth.js  →  shared-ui.js  →  shared-data.js
```
Order matters: later files reference globals (`SUPABASE_URL`, `HOUSING_SESSION`, `CLFN_PERMS`, `sbMapRole`) declared by earlier ones. `shared-config.js` sets a `window.CLFN_CONFIG_LOADED` sentinel checked downstream.

- `shared-config.js` — Supabase URL/anon key, `ROLE` enum, `APP_STATUS` enum, `CLFN_MODULES` (per-nation feature flags), `NATION_CONFIG`
- `shared-auth.js` — `CLFN_AUTH` state object, `HOUSING_SESSION`, `HOUSING_HEADERS`, `resolveHousingRole()`, `doLogout()`, `_clearLocalClientState()`. Pages register `window._onLogout` for page-specific teardown.
- `shared-data.js` — Supabase REST wrappers (`sbLoadApplications`, `sbSaveUnit`, `sbLoadAuditLog`, …), role mapping, `auditEntry()` writing to both in-memory `auditLog[]` and `housing_audit_log` table. All functions are fire-and-forget safe (catch + warn, never throw). Also owns `renderWorklist()` and all contractor modal/print logic (so contractors.html can call it without loading housing-specific modules).
- `shared-ui.js` — view show/hide helpers (`hideAllViews`, `_showView`), nav, `showToast`, `clfnSearchSelect`. **`showToast(msg, opts)` is a persistent message box, not a transient toast.** Messages collect in one dismissible corner panel (`#clfn_msgbox`, self-injected, top-right) that the user closes — per-row **×** plus a **"Clear all"** header button; nothing auto-times-out. Identical repeated messages collapse into one row with a count badge; a 40-row backstop guards against runaway loops. Same signature as before (every existing call site works unchanged): `opts.type` (`'error'`/`'info'`/default) styles the row; `opts.duration`/`opts.position` are accepted but ignored.
- `approval-authority.js` — single source of truth for who can approve what. Use `APPROVAL_AUTHORITY.can(action, role)` / `.who(action)` / `.get(key)` instead of inline `role === 'ed'` checks. Defaults are merged with overrides from `housing_settings` at login.
- `scoring.js` — V2 ED-adjustable scoring model (applications + reno scoring).
- `shared.js` — base utilities loaded first on every page. Also hosts the **`DocLibrary`** component (see below) and the raw-`fetch()` Supabase helper layer.

### My Worklist (`renderWorklist()` in `shared-data.js`)
The landing-page action queue is a single function that renders grouped sections for every item type requiring action. It lives in `shared-data.js` (not housing-init.js) so that all pages that load shared-data can trigger a refresh via `if (typeof renderWorklist === 'function') renderWorklist()`.

**Current sections (in order):**
1. **My Drafts** — draft applications/SOWs/RFQs created by the logged-in user. Each row has two buttons: "Continue →" (yellow) and "Archive" (ghost). Archive helpers are attached to `window` so inline `onclick` strings can reach them: `window._wlArchiveSow(uid, pn)`, `window._wlArchiveApp(appId)`, `window._wlCancelRfq(rfqId)`.
2. **Applications** — submitted/mgr_approved apps for management; returned apps for the owner.
3. **Renovations Waiting Approval** — SOWs needing HM or ED sign-off. HM sees `''`/`'draft'`/`'signed'`/`'submitted'`; ED sees `'hm_approved'` (and can also act on earlier statuses). Clicking opens the SOW modal in-place via `openSowModal()` when available, otherwise navigates to renos.html.
4. **RFQs Open for Bids** — `status === 'issued'` RFQs for management.
5. **Contractors Waiting Approval** — `pending_review` (HE-L2/HM recommends) → `hm_recommended` (**HM or ED** gives final approval; `approveContractor` authority). The recommend step is retained; a role that can both recommend and approve (HM) recommends at `pending_review` and approves at `hm_recommended`, while a pure approver (ED) can approve straight from `pending_review`.
6. **Inventory Approvals** — units where `unitHmSig` is set but `decision` is blank (HM pending), or `unitEdSig` pending / HM deferred to ED. Links to `inventory.html?unit=<id>` which auto-opens the unit edit card.
7. **Ready to Match** — `ed_approved`/`mgr_approved` apps with no assigned unit.

**IMPORTANT — SOW `approval_status` stored values:** The values stored in the database are `''` (empty string, means new/draft), `'draft'`, `'signed'`, `'submitted'`, `'hm_approved'`, `'ed_approved'`, `'completed'`. The labels shown in the renos.html approval table ("Pending HM", "HM Approved", etc.) are **computed from** these stored values — they are never stored. Do not check for `'pending_hm'` or `'pending_ed'` in worklist logic; those strings do not exist in the data.

**Cancelling a Maintenance Request.** Cancel is a **separate terminal state from `approval_status`**: a boolean **`sow.cancelled`** flag (+ `cancelled_at`/`cancelled_by`) — NOT an `approval_status` value — so it never disturbs the approval-chain computation. `cancelSow()` (housing-modals-sow.js, **management-only** via `ROLE.isManagement`) sets it from the **"✖ Cancel Request"** footer button on a saved MR; when the work order was assigned to a **contractor** with an email it prompts (default-on checkbox) to send a **cancellation notice** (`event:'sow_cancelled'`). `sowStatusBadge` renders a red **"Cancelled"** badge that overrides every other state; cancelled MRs are excluded from the active-SOW filters (`hasActiveSows`, `openSowModal`'s activeList) and hidden from the reno-approvals list by default (shown when "show dismissed/archived" is on). Cancelled MRs are **frozen** (`_applySowModalLock` treats them read-only) except for the **ED tier, who can Reopen** (`reopenSow` clears `cancelled` and restores the prior approval status). `saveSOW` **preserves** `cancelled` across edits (it's rebuilt from the form otherwise), so only `cancelSow`/`reopenSow` flip it. Cancelling frees the unit (reverts it from under-repair when no active SOWs remain), same as completing.

**System Approved (RFQ-driven auto-approval).** When an RFQ is awarded, the linked SOW is approved *by the tendering workflow*, not a person (`_rfqApproveLinkedSow` in shared-data.js). To stay compatible with every existing "is this approved?" check, `approval_status` is set to `'ed_approved'` — but the SOW also gets a **`system_approved: true`** flag (plus `approved_via_rfq: true`, `edName: 'System'`). Renders that hold the SOW object (`_card`/`udpRenderSowTable` in housing-modals-sow.js, the contractor SOW list in shared-data.js, and `_getRaApprovalStatusForSow` in renos.html) show an indigo **"System Approved"** badge instead of "ED Approved" when the flag is set. Do **not** count `system_approved` SOWs as manual ED sign-offs. The AI assistant is told the same rule (`ai-chat/index.ts` SOW section).

**`sowApproveInline()`** in `housing-modals-sow.js` — allows HM/ED to approve a SOW from the worklist without leaving the landing page. Shows a confirm dialog, sets the appropriate sig fields (`sow_hm_name`/`sow_hm_date` or `sow_ed_name`/`sow_ed_date`), then calls **`saveSOW()` directly** (Phase RF Tier 4) which handles the approval_status transition and triggers a work-order email if applicable. It deliberately does **not** route through `sowSaveClicked()` — that path adds a *submit*-mode "email a tenant PDF copy" prompt, and approving is not the same as the preparer submitting. So inline approval is two contextual dialogs (approve → work-order email), not three. After final approval the modal closes and `renderWorklist()` refreshes the queue.

**Post-save SOW navigation:** After `sowSaveClicked()` completes, the page does NOT show a "Renovation request updated" dialog. Instead it shows a toast and does a smart refresh: if `#worklist_body` exists → `renderWorklist()`; else if reno approvals view is open → `showRenoApprovals()`. This avoids stranding the user on renos.html when approval was triggered from the landing page.

### Match page (`renderMatchView()` in `housing-views.js`)
Lists applicants ready to be placed in a vacant unit. **Inclusion rules (in order):** not archived; **`existing_tenant` (file update) is never shown** (it's not a housing request and isn't scored); not draft/archived/file_update status; **already-placed apps excluded** (`status==='assigned'` or `assignedUnit` set); **only approved statuses shown** — via the shared **`appIsAssignable(app)`** rule (`mgr_approved` / `hm_approved` / `ed_approved`; see Assignment consolidation below). The two **scored** app types appear: `new_housing` and `transfer_request`.
- **Tenancy is authoritative on the UNIT**, not the application. The view cross-references real tenancy by building lookups (`_housedAddrByAppId` / `_housedAddrByName`) from occupied/reserved `housingUnits` (`assignedTo` / `assignedName`), because an application's `assignedUnit`/`status` are only written back when a unit is assigned to a tenant whose `assignedTo === the application id`. Without this, people housed via other paths (backfilled/legacy tenants, names typed directly, duplicate apps) leaked onto Match as if unhoused.
- **"On Rez" / transfer flag.** A scored applicant who is currently housed (`appType==='transfer_request'` **or** a resolved current tenancy) is **kept** in the queue and flagged with an amber **`🏠 On Rez · <addr>` · transfer** badge under their name; the **Has House** column + sort reflect real tenancy. A housed person surfacing only via a non-scored record is suppressed. `statusLabel` includes `hm_approved → 'HM Approved'`.
- **Placement order (Match Priority, `liveMatchPriorityModel` in `scoring.js`)** is a distinct, ED-adjustable decision from the application **score** (which measures need/urgency): whether a suitable unit exists at all, that unit's **Assignment Type** (see Housing unit fields below), reserve status, and current-housing status decide *who gets matched first*, independent of how urgent their need is. `_matchPriorityOf(a)` (housing-views.js) adds four bonuses on top of `a.score` — `hasMatchBonus` (`bestUnit(a)` is non-null — there's at least one suitable vacant unit for them), `temporaryBonus` (the best-matching unit is a **Temporary** unit), `onReserveBonus` (applicant's `reserve` field === `'On Reserve'`), and `noHouseBonus` (applicant does **not** already have a house, per the same check the **Has House** column uses) — and that sum is the default sort key (`'matchPriority'`, replacing the old `'action'` fallback which had become a no-op once every row in the queue was already assignable). **`hasMatchBonus` dominates first** — an applicant nobody can place today (no suitable vacant unit) drops to the bottom regardless of score/reserve/house/temporary status, even below someone with a much lower score who CAN be placed right now. **`temporaryBonus` stacks on top of the reserve/house tiering below it** — a match against a Temporary (urgent/emergency) unit jumps the queue outright. **Among applicants who do have a match, house status is the dominant split and reserve status secondary** — defaults (`hasMatchBonus: 10000`, `temporaryBonus: 5000`, `noHouseBonus: 2000`, `onReserveBonus: 1000`) rank On-Reserve+NoHouse > Off-Reserve+NoHouse > On-Reserve+HasHouse > Off-Reserve+HasHouse, i.e. an off-reserve applicant with no house outranks an on-reserve applicant who already has one. **When the best-matching unit is a Transition unit**, the applicant's real reserve/house status is ignored entirely and they're scored as if off-reserve with a house (bottom of that tiering) — Transition placements are lower-urgency (demonstrating the tenant can care for a unit) regardless of the applicant's actual circumstances. Every bonus is far larger than the ~100-point max application score, so within any tier the highest score always wins. Settings → App Settings → Scoring has a **"Match Priority"** card (`renderMatchPriorityEditor()`) to tune or disable any of these factors (set to 0 to remove one; all 0 falls back to pure score ranking); persisted to `housing_settings` key `match_priority_model` (merged over the defaults on load so a model saved before a new bonus was added still gets it), hydrated into `window.liveMatchPriorityModel` at boot the same way `scoring_model_v2` hydrates `liveV2ScoreModel`. **Gated by its own `editMatchPriority` approval authority** (default `['ed']`, Settings → Approval Authority → Scoring group) — deliberately separate from `editScoreModel` so an ED can delegate *who gets matched first* independently of who can edit the application's need/urgency scoring model. `saveMatchPriorityModelED()`/`resetMatchPriorityModelED()` use a dedicated `_matchPriorityGuard()` (scoring.js) rather than the shared `edGuard()` helper, since `edGuard` is hardwired to the `editScoreModel` check and is reused by several other scoring-adjacent settings (V2 tiers, unit/reno scoring) that aren't part of this delegation.
- **Bedroom-size eligibility ceiling.** A unit **one size up** from what an applicant needs (e.g. a 2-bed for someone who needs 1) is a normal, freely-assignable match — scores the same `+5` it always has. A unit **two or more sizes up** (e.g. a 3-bed for a 1-bed need) always requires **`overrideMatch`** (ED) approval to assign, regardless of what else is available — this doesn't ride on the pre-existing score-relative "tied band" mechanism (which only compares a unit to whatever else happens to be vacant, and would wrongly let an all-oversized vacant pool through since they'd tie with each other), and doesn't depend on there being a better option. `_isOversizedUnit(u, needsBeds)` (housing-init.js, `bedrooms >= needsBeds + 2`) is checked two ways: (1) as an explicit, unconditional hard gate in `confirmAssignment()` — independent of the tied-score check entirely; (2) folded into `amSelectUnit()`'s `isTied` computation (`isTied = ...within 1pt... && !isOversized`) so the modal's UI (button state, warning text, notes requirement) shows the existing "ED Approval Required" treatment for oversized picks even when their raw score happens to tie with other options. `_scoreUnit()` (housing-init.js, the actual Assign-Unit-modal scorer) and `bestUnit()` (housing-views.js, the Match page's recommendation display) both score 2+-oversized units at `-50` (previously a flat `+5`, identical to one-up) so an oversized unit is never shown as an equally-good recommendation.

### Scroll-collapse (info strips + KPIs + list-page headers shrink on scroll)
A tablet/mobile space-saver modeled on the MyChart (Epic) patient-portal pattern: a hero/tile row shrinks to a compact glance-only bar once the user scrolls into content, and expands back near the top. Purely visual — one shared JS helper flips a class; CSS owns what "collapsed" looks like per element type.
- **`_initScrollCollapse(scrollEl, stripEl, opts)`** (`shared-ui.js`) is the single implementation all surfaces share. It's a passive, rAF-throttled scroll listener that toggles `.is-scrolled` on `stripEl` once `scrollEl`'s scroll position (or `window.scrollY` if `scrollEl === window`) passes a 16px threshold (`opts.threshold` to override). **Idempotent** — guarded by `stripEl.dataset.scrollCollapseWired`, so callers can invoke it unconditionally on every render/open without double-wiring.
- **Modal info strips** — the TIC (`housing-tic.js` `_ticWire()`), Edit Unit modal (`housing-modals.js` `openUnitEditModal()`), and Maintenance Request modal (`housing-modals-sow.js` `openSowModal()`) all wire `_initScrollCollapse(modal.querySelector('.tic-body'), modal.querySelector('.tic-strip'))` — the tab body is each modal's own internal scroll container, and the strip sits outside it (always in DOM flow), so this is a space-reclaiming shrink-in-place, not a "bring back what scrolled away" sticky header. Each `.tic-strip-tile` carries a hidden `<span class="tic-strip-icon">` glyph (chosen per tile — e.g. Status 🛠️, Est. Cost 💰, Assigned To 👷, Target Completion 📅 on the Maintenance Request strip); `.tic-strip.is-scrolled` (housing.css) hides the label/value text and shows the icon, per the user's chosen "icon-only row" style (over a single-line text-summary alternative).
- **Dashboard KPI strip** (`#landing_kpi_strip` on `housing.html`) — wired from `_renderLandingKpis()` (housing-views.js) against `.content-area` (the page-level scroll container every page uses). Each `.kpi-card` carries a hidden `.kpi-icon` span; `.kpi-strip.is-scrolled` (shared.css) hides `.kpi-label`/`.kpi-value`/`.kpi-meta` and, for the "Applications by Type" card, the `.kpi-breakdown` wrapper (added specifically so its nested 3-row breakdown has something to hide as a unit) — same icon-only-on-scroll behavior as the modal strips.
- **List-page headers** (Inventory, Match, Tenants only) — wired from each page's own render function (`renderInventoryView`/`renderMatchView`/`renderTenantsView` in housing-views.js) against `.content-area`, targeting that page's own `.page-header-bar`. `.is-scrolled` (shared.css, scoped to `#inventoryView`/`#matchView`/`#tenantsView` specifically) hides the `.phb-title p` subtitle and shrinks the `.phb-title h1` — `.phb-actions` (buttons) stay untouched/visible throughout. Deliberately **not** a blanket `.page-header-bar` change: those three are list pages where the header competes with the list for vertical space; other `.page-header-bar` users (renos, rfq, contractors, inspections, finance) are unaffected.

### Assignment consolidation (Phase WF, `shared-data.js`)
The application → unit assignment flow has **one shared approval rule** so the four assignment paths can't drift:

### Finance module data layer (Phase F3, shipped)
- `_FIN_TABLES` registry maps each in-memory collection (tenants, rentLedger, loanList, …) to its Supabase table + camelCase↔snake_case mapper.
- `_bootLoadFinanceData()` fetches all tables in parallel at DOMContentLoaded and hydrates `_memStore`.
- `loadData()` / `getData()` stay synchronous and return `_memStore` by reference — ~125 call sites in `finance.html` were not rewritten.
- `saveData(d)` is synchronous to the caller; internally diffs vs previous `_memStore` and fires async upserts/deletes. Failures show a persistent red toast; success is silent.
- `uid()` returns `crypto.randomUUID()` (matches Supabase `uuid` columns).
- Every `saveData` writes one audit row to `finance_audit_log` via `_writeAuditEntry()`. Per-action audit (approveLoan, postPayment, …) uses the public `writeAuditEntry()` wrapper.

- Voids vs deletes: ledger tables use a void pattern (reversing entry with `voids_id` FK); entity tables use soft-delete (archived flag). The UI surfacing of this is Phase F3B (pending).

### Tenant data
- `tenants` is a platform-level table shared by housing + finance, trigger-synced from `housing_units.assigned_name`. Backfill ran at the F2 migration. Don't insert tenant rows by hand for production data — change `housing_units.assigned_name` and the trigger handles it.
- The current `tenants` schema is slim: housing-specific fields (unit type, rent amount, hydro/gas accounts, autoPay, …) aren't there yet and default to empty/false on load. Phase C will reconcile.
- **Person identity / duplicate roll-up (`merged_into`).** The sync trigger inserts a **new** `tenants` row per assignment and never matches by name, so one person accumulates several rows over time (migration `20260624_tenants_merged_into.sql`). `merged_into` points a duplicate at the canonical person's row (NULL = canonical). The housing-side **⇉ Merge Duplicates** tool (`openTenantMergeManager` in `shared-data.js`, on `tenants.html`, `mergeTenants` authority) sets it; it's reversible (it never deletes). **Finance respects this end-to-end:** `_tenantFromRow` loads `mergedInto` and `_tenantToRow` preserves it; at boot `_finCanonicalizeTenantRefs()` (finance-data.js, runs before the payment-derive pass) rewrites every child row's in-memory `tenantId` (rentLedger/loanList/arrangements/collections/journalEntries; loan/arr payments inherit via their parent) to the canonical id, so all ~60 per-tenant filters, `calcAllTotals`, the profile, the FIC and dashboards aggregate under one person. The **original id is kept on `row._rawTenantId`** and written back by the `toRow` mappers, so a save never repoints the DB (the merge stays reversible). Merged-away rows are hidden from the finance tenant list, search (`finHomeSearch`), pickers (`finVisibleTenants()`), and batch/rent-run invoicing (so a duplicate is never billed). `getTenant(id)` / `finCanonTenantId(id)` (finance-utils.js) resolve a merged id to the canonical person. **The merge is the real fix for duplicate lines; the finance search also dedupes un-merged same-name+unit rows for display.**

### Housing unit fields
Unit records (`housing_units`) have these non-obvious fields:
- `deptNumber` — Department Number (cost-centre for capital budget tracking)
- `acctNumber` — Account Number for recurring charges (rent, utilities). Has a tooltip in the UI.
- `insuredValue` — Insured Value (formerly "Construction Cost"). All unit types.
- `cmhcValue` — CMHC Value. Only enabled when `funder === 'CMHC_95'`; null otherwise. `ueFunderChanged()` in `housing-modals.js` enforces this gate.
- `unitHmSig` / `unitEdSig` — HM/ED approval decisions on the unit's renovation budget. Each is `{name, date, decision, notes, savedAt}`. Decision values: `'approved'`, `'declined'`, `'deferred'` (HM only — escalates to ED). These are saved only when a name or decision is entered in the unit edit modal; null means no approval has been initiated. The approval blocks in the unit edit modal are shown/hidden by `ueUpdateBudgetRouting()` based on SOW total cost vs. the HM budget limit (`hmBudgetLimit` in settings, default $25k).
- `latitude` / `longitude` — decimal map coordinates for the unit. Set via the TIC "Set Location & Photo" (SLP) flow or the bulk geocode script (see TIC section). The TIC Overview tab renders an OpenStreetMap embed from these; null shows a "Coordinates not yet set" placeholder.
- `hydro_meter_number` / `gas_meter_number` — utility meter numbers. These live on `housing_units` (not `tenants`); the hydro/gas **account** numbers still live on `tenants`. Edited from the TIC Utilities tab; fields with `saveTarget: 'unit'` PATCH to `housing_units`.
- `assignmentType` — `''`/blank (Regular/permanent, default), `'temporary'`, or `'transition'`. Set via the **Assignment Type** dropdown in the Edit Unit modal's Overview tab (`ue_assignment_type`, read/written in `housing-modals.js`'s `openUnitEditModal()`/`saveUnitEdit()`). No SQL migration needed — like `hydro_meter_number` before its dedicated column existed, this flows through the `data` jsonb blob `sbSaveUnit`/`sbLoadUnits` (shared-data.js) already round-trip for every unit field. Shown as a **TEMPORARY** (red) or **TRANSITION** (blue) badge next to the address on Inventory (table + cards) and Tenants (table + cards), mirroring the ELDERS UNIT badge pattern (`_assignmentTypeBadge()` in housing-views.js). **Temporary** units are for urgent/emergency placements; **Transition** units are for tenants demonstrating they can care for a unit (lower urgency, probationary). Both feed into Match Priority — see below.

### Tenant Information Card (TIC) & maps (`housing-tic.js`)
The TIC is a self-contained IIFE full-screen modal opened via `window.openTenantCard(idOrUnitId)` / closed with `window.closeTenantCard()`. **Tabs:** Overview, Utilities, Documents, Unit History (and tenant detail fields). `_ticRenderOverview()` / `_ticRenderUtilities()` render the panels; a known footgun is the DocLibrary not mounting until its tab is actually shown (several fixes around tab-switch mounting).

**Notes.** TIC notes ("Add a Note" on the Notes tab) save to **`tenant_notes`** (keyed by `tenant_id`) via `_ticSaveNote` → `_ticEnsureTenantRow` (creates the tenant row on first write for applicant TICs). The Notes panel *displays* a merge of `tenant_notes` + intake `housing_application_notes` (loaded read-only via `sbLoadAppNotes`), but adds always go to `tenant_notes`. The **hero shows a last-note-age badge** (`_ticLastNoteInfo`, red when there are no notes or the newest is > 90 days old) so staff keep files current. **Reusable workflow note prompts:** `promptTenantNote(name, opts)` / `sbSaveTenantNote(name, body, opts)` / `sbResolveTenantId(name)` in `shared-data.js` let any flow capture an optional note against the tenant file — wired into **move-in** (`confirmAssignment`), **work-order completion** (`markSowComplete`), and **inspection approval** (`saveInspection`). `sbResolveTenantId` is find-first (avoids minting duplicate trigger-synced tenant rows); all are fire-and-forget safe.

**Field save routing:** TIC fields carry a `saveTarget` (`'unit'` → PATCH `housing_units`; otherwise the `tenants` row). On `'unit'` save success the in-memory `housingUnits[]` cache is kept in sync. Hydro/gas **meter** numbers save to `housing_units`; hydro/gas **account** numbers save to `tenants`.

**Tenancy Status → BCR sync.** `TIC_TENANCY_OPTIONS` (Overview tab) includes `'banished'` and `'harbouring'` alongside the lifecycle values (active/vacated/transferred/evicted/suspended/deceased/bankrupt). Setting a tenancy's status to **Banished** calls `_ticSyncBanishedToBcr()`, which keeps this in sync with the separate, name-keyed **`bcr_registry`** (Band Council Resolution ineligibility list — see shared-data.js's BCR section) that's actually enforced as a warning gate at application-approval/unit-assignment time. It never silently writes a registry row (no date/reason to fill in from here): if the person isn't already on the list it opens `openBcrManager(name)` pre-filled, gated the same as the BCR list itself (`manageBcr` authority, HM/ED) — non-authorized staff just get a toast telling them to ask HM/ED. **Harbouring** (housing/sheltering someone who is on the BCR list) is a plain status label with no additional linked behaviour.

**Maps — two distinct widgets:**
- **TIC Overview map (read-only)** — a static OpenStreetMap `export/embed.html` **iframe** built from the unit's `latitude`/`longitude`. No Leaflet on this widget. Requires `frame-src https://www.openstreetmap.org` in CSP (`_headers`).
- **Set Location & Photo (SLP) modal (interactive)** — an ED/admin tool to set a unit's pin + photo. Lazy-loads **Leaflet 1.9.4** (cdnjs) and **exifr** (`cdn.jsdelivr.net`) on demand via `_slpLoadScript()`. Coordinates can be set three ways: clicking/dragging the Leaflet pin, the browser Geolocation API, or **EXIF GPS** auto-extracted from an uploaded photo (`exifr.gps(file)`). `_slpSave()` PATCHes `latitude`/`longitude` to `housing_units` and uploads the photo. Self-contained so it works when launched from the worklist.

**Bulk geocoding:** `geocode-units.ps1` (run by the user on Windows, **not** in CI) back-fills coordinates for units missing them. Uses the **OSM Nominatim** API (OCAP-friendly: no Google, no API key), rate-limited to ~1 req/sec, authenticating to Supabase with the **service-role** key (passed via `-ServiceRoleKey`). Unmatched units are listed for manual entry.

**Occupancy agreement / lease modal (`_ticOpenLeaseModal(docKey)`, Phase WF).** The TIC generates the residential/temporary/commercial agreement (parameterized by `_ticLeaseDocKey`; clauses from `CONTRACTS_DOCS_REGISTRY` in notifications.js). Non-obvious behaviour:
- **No unit = no agreement.** The modal requires `_ticState.unit && _ticState.unit.id`; address/unit details come from the unit card. Occupants come from the application's `habitants`, not an editable Schedule A. Rent is resolved ledger → unit → tenant → application and shows a **rent-source label**.
- **Auto-open hand-off.** `confirmAssignment` (after assigning a tenant) sets `window._ticAutoLease = 'residential_lease'` and opens the TIC; `openTenantCard` reads+clears the flag and auto-opens this modal pre-filled once the tenant/unit/application resolve.
- **Inline initials (Tier 4).** Each required clause renders an inline Draw/Type/Wet pad (`ls_init_<i>`) in the modal — no more separate full-screen pop-outs (the old `_ticOpenInitialsPopout` walker is left defined but unwired). `_ticCaptureInlineInitials()` reads the pads into `_leaseInitials` **keyed by clause id**, so the two PDF generators (jsPDF saved-body path + PDFLib `lease-001.pdf` template path) are unchanged.
- **Readiness gate (Tier 2, split hard/soft).** `_ticGenerateLeasePdf` calls `_ticLeaseMissingHard()` first — only a missing fixed-term end date hard-blocks (shows `_ticShowLeaseChecklist` and stops), since the document would otherwise print with a core term literally blank. Missing initials/signatures (`_ticLeaseMissingSigs()`) are a **soft** check — a `showConfirm` "Generate without all signatures?" prompt lets staff generate an unsigned/partially-signed copy anyway (e.g. to sign on paper), mirroring the RFQ contract gate's `_rfqContractMissingSigs()` pattern in `rfq.js`.
- **Draft persistence (Tier 2).** Closing via `_ticCloseLeaseModal` snapshots initials + signatures into `_leaseDraft` (keyed `docKey|unitId`); reopening restores drawn/typed/wet marks via `_ticRestoreSig`. Signatures use the shared `_initSigPad`/`getSigDataURL` engine.

### DocLibrary (shared document component, `shared.js`)
`window.DocLibrary.create(mountEl, opts)` is the reusable per-entity file manager used across the app: application Step 6 docs, the scorecard, TIC tenant + utility-bill docs, unit detail panels, finance tenant profiles, and RFQ documents. Files go to Supabase **Storage** (bucket `STORAGE_BUCKET`, default `'housing-files'`) under an entity-scoped `pathPrefix` (e.g. `units/<id>/utility-bills`); every upload/delete/category-change writes an audit row to `housing_audit_log` (`file_uploaded` / `file_deleted` / `file_category_changed`).

- **Categories** come from `opts.categories` (key/label/icon) and drive the filter chips. An **`Image`** category (`🖼️`) is in every document-type dropdown so photos can be filed alongside PDFs.
- **Inline category editing:** when not `readOnly`, each file row shows a category `<select>`; changing it calls `_updateCategory()` which re-files the doc and writes the audit row.
- **Optimistic insert:** the file list is derived from `housing_audit_log` (`_loadMeta`), so a just-uploaded file used to "not show at first" until the audit re-read caught up. After a successful upload+metadata write the file is added to `state.files` immediately and tracked in `state.pendingUploads`; `refresh()` merges pending uploads the server read doesn't yet reflect and drops each one once the server confirms it (delete clears it from pending so it can't be resurrected).

### Degraded mode (slow / flaky cell connections, `shared-data.js`)
Every save promise is wrapped by `_withSaveTimeout()` with a hard **10 s** timeout (`_SAVE_TIMEOUT_MS`). A timeout while the device still reports `navigator.onLine === true` calls `_enterDegradedMode()`, which sets a **30 s** cooldown (`_DEGRADED_COOLDOWN_MS`), queues saves locally via `saveQueueAdd()`, and toasts "Slow connection — saving locally…". During the cooldown all saves skip the network and queue immediately. `_runDegradedProbe()` HEAD-pings Supabase after the cooldown: success exits degraded mode and flushes the queue; another timeout extends the cooldown. The browser `online` event also clears degraded mode immediately and syncs. Implemented with a simple `Promise.race` + `setTimeout` — no `AbortController` or `navigator.connection`.

### RFQ module (`rfq.html` + `rfq.js`)
RFQs (Requests for Quotes) link a SOW to one or more contractors who are invited to bid.

**Data:** Stored in `housing_rfq` table. Loaded at boot into `window._rfqCache` (keyed by `rfq.id`) in both `housing-init.js` (for the worklist/search) and `rfq.js` (for the full RFQ page). `rfq.data` is a JSON blob holding all the form fields that aren't top-level columns. **Numbering (Phase RF Tier 4):** RFQ numbers (`RFQ-YYYY-NNNN`) are generated by scanning the in-memory cache, so `saveRfqDraft`'s **first** save of a new RFQ uses a **collision-safe insert** (plain POST that errors on a duplicate id → bump the number and retry ≤6×) instead of a destructive `merge-duplicates` upsert; edits keep the upsert. A true server-side sequence is the remaining fully-race-proof option (would need a Supabase migration). `CON-` contract numbers live in `rfq.data` (not a PK) so they carry no overwrite risk.

**Status flow:** `draft` → `issued` → `awarded`, and **`cancelled` from any stage including `awarded`** (a contracted job that falls through). `cancelRfq` (rfq.js) is offered from the list row and the form's **Cancel RFQ** button; cancelling an **awarded** RFQ prompts (default-on checkbox) to email a **cancellation notice** to the awarded contractor (`event:'rfq_cancelled'`, inline `sendNotification` like `awardRfq`). Cancelling an RFQ does **not** auto-cancel the linked MR/SOW — they're independent cancel actions. **Bid amounts flow through:** the awarded contractor's recorded bid (Recipients tab `_rfqBids`) auto-populates the Scope Award card's Award Amount via `_rfqSyncAwardAmountFromBid()` — fired both when the awarded contractor is selected (`_rfqAutoFillContractor`) and when their bid is edited (`_rfqSetBidAmount`) — so the quote flows into the award and the generated contract without re-keying. The worklist shows `issued` RFQs. The list-row **Edit** button and the **Issue** button are draft-only, but an HM/ED opening a non-draft RFQ still gets an editable form **by design**: bids are recorded on `issued` RFQs (Bids Received card) and the Contracting tab is filled after `awarded`. Caveat: editing an issued RFQ's scope/recipients does **not** re-notify contractors who already received the emailed package — the ED "Unlock RFQ" (back to draft) + re-issue path is the correct way to materially change an issued tender.

**Edit permission — HM/ED only (read-only for everyone else).** `_rfqCanEdit()` (rfq.js) returns true only for `housing_manager` and `ed` (via `normalizeRole`). `_rfqApplyReadOnly()` runs on form open and after every tab render: it disables all inputs/selects/textareas and mutation buttons (keeping the tabs, Back to List, and Preview PDF — marked `data-rfq-keep`), shows a **"🔒 View only" banner** (`#rfqReadOnlyBanner`), hides the dynamic-row remove buttons (CSS `#rfqFormView.rfq-readonly … button`), and passes `readOnly` to the Documents `DocLibrary`. Defense-in-depth guards also sit at the top of `saveRfqDraft`/`issueRfq`/`unlockRfq`/`cancelRfq`/`confirmAward`/`_rfqManualAward`/`generateContractorContract`. RFQs are linked to the unit via the inventory panel's "RFQs & Contracts" section (`udpRenderRfqSection` → `rfq.html?rfq=<id>`), so anyone can open one to view; only HM/ED can change it.

**Awarding approves the linked SOW.** `awardRfq` (shared-data.js) is `async` and calls `_rfqApproveLinkedSow(rfq.sow_unit_id, rfq.sow_project_number, role)` so a completed tender marks the SOW **System Approved** (see the SOW `approval_status` note above). It accepts `opts.skipNotify` to suppress the winner + regret emails. Two award paths: (1) the **"Award →"** button on the Recipients tab runs the full app tender (emails winner + regret notices); (2) **"Record Award & Approve SOW — No Notifications"** on the Scope tab's Award card (`_rfqManualAward`) is for tenders run manually/offline — it records the award with `{skipNotify:true}`, approves the SOW, and opens Contracting, emailing no one.

**Tabs on `rfq.html`:**
- **Details** — RFQ number (auto-generated), linked SOW/unit, issue date, closes date, contact info, scope description. The **Scope Summary** auto-prefills from the linked SOW's work items for a new RFQ (`_fetchAndPopulateSow`, Phase RF Tier 1).
- **Scope** — structured scope-of-work items (checkboxes per category)
- **Recipients** — contractor selection (`_rfqSelectedCts` keyed by contractor id). Selecting contractors here populates `recipient_contractor_ids[]` on the RFQ record and drives the RFQ letter email. Also hosts the **Bids Received** card (see Tendering below).
- **Documents** (`_rfqDocLib`) — `DocLibrary` instance attached to this RFQ's unit. Files uploaded here also appear on the unit card in inventory. Selected documents can be attached to the RFQ email sent to contractors.
- **Contracting** — Contract Details (contract number, scope, pricing breakdown, milestone payments), dynamic rows (materials/specs, exclusions, nation-supplied items), signature blocks (nation rep + contractor). **No witness signature block.** Generate Contract button produces a jsPDF document. `generateContractorContract` has a **readiness gate** (`_rfqContractMissing` hard-blocks on awarded contractor / price / contract date / completion date via `_rfqShowChecklist`; missing signatures are a **soft** confirm — Phase RF Tier 2).

**Tendering — staff-entered bids (Phase RF Tier 3).** The system records quotes and awards from them (no contractor-facing portal — that's deferred behind RLS). Bids live in `rfq.data.bids` (keyed by contractor id: `{amount, notes, received_at}`; `_rfqBids` state) — **no schema change**. The **Bids Received** card (`renderBidsSection`) on the Recipients tab shows one row per invited contractor (amount/notes/received inputs), **sorted ascending with the lowest bid highlighted**, each with an **"Award →"** button. `_rfqAwardFromBid` saves first then opens the award modal **prefilled** with the contractor + quoted amount. On award, `awardRfq` (shared-data.js) emails the winner **and serialized regret notices to the other bidders** (sequential await, detached — respects the Graph ~4-concurrent throttle). `confirmAward` first shows an **eligibility warning** (`_rfqContractorEligibility`) when the winner is un-approved or has expired WSIB/insurance (warn, not block). Awarding then offers a **"Set up contract →"** hand-off that re-opens the Contracting tab and seeds it from the award (`_rfqSeedContractFromAward`: awarded contractor + signatory + contract price). The **RFQ-button threshold** is the shared `_sowMeetsRfqThreshold` (shared-data.js, reads `.amount`/`.totalCost`/`.cost`), used by both the SOW modal and the `renos.html` approval table.

**Contract numbers:** Auto-assigned format `CON-YYYY-NNNN` (4-digit sequential). `generateContractNumber()` in `rfq.js` scans `_rfqCache` for the highest existing `CON-{year}-` number and increments. Stored in `rfq.data.contract_number`; the field is readonly in the UI.

**Contracting tab dynamic rows:** Materials & Specifications, Exclusions, Items Supplied by Nation, and **Subcontractors** all use dynamic row arrays (add/remove rows). These live in `rfq.data` as arrays and are rendered by `render*Rows()` functions. **Subcontractors** (`subcontractor_rows`: `{contractorId, name, trade, scope}`) are picked from the **contractor registry** (`_rfqSubOptions` builds a `<select>` of `window._contractors`; `_rfqOnSubContractorChange` snapshots the name/trade so the contract prints even if the registry later changes), with a live WSIB/insurance compliance flag per row via the shared `_rfqContractorEligibility(ct)`. The generated contract (`_rfqBuildContractPdf`) prints a Subcontractors table **plus a mandatory clause** requiring every sub-trade to provide a valid WSIB clearance certificate and proof of ≥ **$2,000,000** Commercial General Liability insurance before starting work (the clause prints even when no subs are listed).

**Generated contract PDF:** Uses jsPDF with the standard nation header (logo + contact info from Settings → Nation) and footer (Page X of Y). Contract body includes all Contracting tab sections. Saved contracts are uploaded once to Storage and filed in **both** document libraries: the unit's (file-meta entity `'tenant'`, so it appears on the inventory unit card) **and** this RFQ's (file-meta entity `'rfq'`, so it appears on the RFQ → Documents tab — `_rfqDocLib.refresh()` is called so it shows immediately). Both DocLibraries share the `tenants/<unitId>` path prefix, so a single stored object surfaces in both.

### Renovation Questionnaire (`reno-questionnaire.js`)

### Audit log attribution
`auditEntry(appId, action, detail, user)` stores the logged-in user's **email** (from `HOUSING_SESSION.email`) in the `actor` column, not the role string. `sbLoadMyRecentActivity(limit)` queries with `?actor=eq.<email>` to return only the current user's entries. This means audit entries created before the email-attribution change will not appear in "Recent Activity" (they have role strings instead of emails in the `actor` column).

### Idle timeout
`_idleLogout()` in `shared-auth.js` clears `sessionStorage` tokens **immediately and synchronously**, then fires `doLogout()` as a detached async (fire-and-forget), then redirects to `index.html?timeout=1` synchronously. Do NOT await any network call before redirecting — the blank-page bug was caused by awaiting the Supabase sign-out before navigation. `auth-login.js` checks `?timeout=1` on load and shows `#timeout-banner`.

### Session-expiry redirect (401 interceptor)
Separate from the idle timeout: a dead/expired JWT mid-session should land the user on the login screen, not strand them on a page making failing calls. `shared-auth.js` defines **`_handleSessionExpired()`** (mirrors `_idleLogout`'s safe teardown — synchronous token clear → detached sign-out → immediate `index.html?timeout=1` redirect, **never** awaiting network) and installs a **global `fetch` interceptor** (idempotent, guarded by `window._authFetchWrapped`). On a **401** from a Supabase REST/Storage/Edge-Function call (skips `/auth/v1/` so login + refresh failures don't trip it; only fires when `HOUSING_SESSION.accessToken` exists), it attempts **one** `refreshHousingToken()`; success self-heals silently, failure calls `_handleSessionExpired()`. **PostgREST returns 403 (not 401) for RLS/permission denials**, so this never misfires on those. **Slow-connection save timeouts are deliberately untouched** — they stay in the offline queue / degraded mode so field staff don't lose work. Loaded on every page (all HTML pages load `shared-auth.js`).

### Email notifications
- Outbound transactional email goes through a Supabase Edge Function at `supabase/functions/send-notification/index.ts`. The function verifies the caller's JWT, then sends via a **per-nation provider** chosen by the `EMAIL_PROVIDER` secret — `graph` (default, **Microsoft Graph** / M365), `resend`, or `sendgrid` — and writes an audit row via service_role. For Graph it uses OAuth2 client_credentials against the Entra app `CLFN Housing App — Notifications`, FROM the `housing@clfn.on.ca` shared mailbox. For Resend/SendGrid it uses `EMAIL_FROM`/`EMAIL_FROM_NAME` + the provider API key. Footer brand + reply-to come from `EMAIL_BRAND`/`EMAIL_REPLY_TO` secrets or the client's `brand`/`reply_to` payload (injected from `NATION_CONFIG` in `sendNotification`). This lets nations without M365 send mail (Phase N1). Source must stay **ASCII-only**. Graph's Application Access Policy NOT yet applied (Mail.Send is tenant-wide; PowerShell snippet ready but hardening item is open).
- Required Edge Function secrets: `GRAPH_TENANT_ID`, `GRAPH_CLIENT_ID`, `GRAPH_CLIENT_SECRET`, `GRAPH_FROM_USER`. The Graph token is cached in-memory per Edge Function instance.
- Function accepts an optional `attachments[]` payload field (`{name, contentType, contentBytes}` per item) — passed through to Graph as `#microsoft.graph.fileAttachment` entries. Used today for the applicant PDF copy. Graph caps a single fileAttachment at ~3MB.
- Edge Function source must stay **ASCII-only**. Em-dashes, box-drawing, and other non-ASCII chars have broken the dashboard editor's parser before. Verify with `grep -P "[^\x00-\x7F]"` before pasting.
- **Client API** is `window.sendNotification(opts)` in `shared-data.js` — generic Edge Function wrapper. Per-event composition + recipient resolution lives in `notifications.js` (`EMAIL_EVENT_REGISTRY`, per-entity token builders, `_renderEmailTemplate`, `notify<Event>()` helpers). Add a new workflow notification = add a registry entry (incl. `defaultRecipientRoles` + `defaultCcRoles`) + a `notify<Event>(entity)` helper that calls `_sendSerially` + invoke it from the firing point with a `typeof === 'function'` guard. The Settings → Notifications tab auto-renders the registry for editing.

- **Recipient resolution** combines primary + CC roles via `_resolveActiveStaffForRoles` (deduped by lowercased email). Roles must match canonical strings: `ed`, `housing_manager`, `housing_employee_l2`, `housing_employee_l1`, `cfo`, `finance_l1`. Legacy strings like `'hm'` won't match — normalise via SQL.

Unified two-section layout across every event: **Recipients** (primary role checkboxes; `recipientType: 'applicant'` / `'tenant'` / `'contractor'` events also show a fixed "always sends to …" info line above the grid and the "pick at least one role" validation is skipped) + **Optional CC** (role checkboxes, always optional). Saved overrides live in `housing_settings` row `key='email_templates'` as `{subject, bodyHtml, recipientRoles[], ccRoles[]}` per event, cached as `_appSettings.email_templates`.

2. **Draft with AI** — `aiDraftNote()` fills the approval-modal notes box (`#approvalModal_notes`) with a professional decision note for the current application + action.

- **Data model is context-stuffing PLUS a read-only query tool.** The client (`ai-assistant.js`) gathers app/unit/SOW/RFQ/contractor/reno-progress data from in-memory globals (`window.applications`, `housingUnits`, `_sowCache`, `_rfqCache`, `_contractors`, `_renoProgress`), trims/flattens it, and POSTs it as `context` to `ai-chat`. For quick questions Claude answers from that context; for **exact counts / complete lists / records not loaded on the current page**, chat mode also exposes a read-only **`query_database`** tool (tool-use loop, chat mode only — `draft` mode is a single call). The tool reads via the service-role key but is gated by a **per-table role allowlist** (`TABLES`): `housing_applications`/`housing_rfq` are MGMT-only (hidden from field employees); `finance_*` is ED/CFO/Finance only; `housing_audit_log`/`staff` are ED/HM only; the rest (`housing_units`, `tenants`, `housing_contractors`, `inspections`) are all staff. Hard caps (`MAX_ROW_LIMIT=50`, `MAX_TOOL_TURNS=6`), whitelisted filter ops (`SAFE_OPS`), regex-validated names. **No write tools exist.** **Real-schema gotchas baked into `TABLES`:** the SOW table (`housing_sow`) is **deliberately not queryable** — it stores one row per unit with all SOW details in a `data` jsonb array, so SOW/work-order questions are answered from the client context; `housing_applications` keeps the applicant name + household fields in a `data` jsonb (only status/score/tier/app_type/etc. are top-level columns); several tables (`housing_units`, `housing_rfq`, `housing_contractors`) keep extra fields in a `data` jsonb. The model is told to `select=*` with a small limit when it needs columns that aren't top-level. The **how-to guidance lives in the `HOW_TO` block** in `ai-chat/index.ts` — the canonical place to add/adjust workflow instructions (keep it ASCII, grounded in the real UI).
  - **SOW/RFQ context shape (must match the real caches).** `_sowCache[unitId]` is a `{sows:[…]}` wrapper — one entry **per SOW** — so `ai-assistant.js` iterates `.sows`, not the wrapper (an earlier bug read fields off the wrapper and sent blank status/total). Each SOW is flattened with `approval_status`, `approved`, **`system_approved`** / `approved_via_rfq` (so the model labels RFQ auto-approvals "System Approved", not "ED Approved"), `project_number`, `assigned_team`, contractor, total, item_count. RFQ context uses the real columns (`sow_unit_id`, `sow_project_number`, `awarded_contractor_id`, `award_amount`, `contract_number` from `data`) — not the old `unit_id`/`contractor_name`/`total_amount`. The `ai-chat` SOW-section prose and the `housing_rfq` `cols` hint carry the matching guidance; **the Edge Function must be redeployed** (Supabase dashboard paste or `supabase functions deploy ai-chat`) for prose changes to take effect — the client context fix is live on normal deploy.
  - **Staff activity / "who was active" reports and the 50-row cap.** Every login writes a `housing_audit_log` row (`action: 'user_login'`, written client-side by `_recordSessionLogin()` in `shared-auth.js`, once per browser session) — the underlying data is reliable for every role, RLS blocks UPDATE/DELETE but not INSERT. The failure mode is downstream, in how the model queries it: `order=created_at.desc` + `MAX_ROW_LIMIT=50` means one busy staff member's ordinary activity (SOW/RFQ auto-saves, notifications) can fill the entire 50-row window with their own rows, silently pushing every other staff member's once-a-day login row out of the result set — the model then wrongly concludes "only X was active." The system prompt now tells it to query `action=eq.user_login` (rare, won't hit the cap) filtered to the date in question rather than a generic recent-rows dump. Same redeploy caveat as above.
- **Security (hardened):** the function requires a **valid Supabase user JWT** (the client sends `HOUSING_SESSION.accessToken`, not the anon key) and resolves the caller's role from the `staff` table (`is_active=true`); non-staff get 403. The verified role overrides any client-supplied `ctx.role`. This stops anon-key abuse of the paid Anthropic call. The **`ANTHROPIC_API_KEY` lives only in function secrets**. **ASCII-only source** (verify with `grep -P "[^\x00-\x7F]"`). The client must send the user token for the function to accept the call — redeploy the function and the client together.
- **AI audit logging (server-side).** Every AI interaction writes **one append-only row to `housing_audit_log`** from inside `ai-chat` (service-role, so a tampered client can't skip it). `actor` = the JWT-verified email; `action` = `ai_query` (chat) or `ai_draft` (draft notes); `entity_type` = `ai`, `entity_id` = `AI`; `detail` is a JSON string with a human-readable summary (so the existing audit-log UI renders it via `_parseAuditRow`'s `d.detail`) plus structured fields (`name`, `mode`, `role`, `question`, `reply_chars`, `tables_queried`, `turns`). Wired into all return paths (draft / chat answer / loop-exhausted), awaited before responding (so the insert completes before the instance is reclaimed) but never throws into the request path. `housing_audit_log` is already in the AI's read allowlist (ED/super_user/HM), so the assistant can report on its own usage. No schema change (reuses existing columns); no new secret.
- **`app_type` semantics (used by the Match page + AI).** `housing_applications.app_type` is one of: `new_housing` (seeking a new unit; **scored & ranked**), `existing_tenant` (a **file update** only — NOT scored, **never** on Match), `transfer_request` (a current tenant who **already has a house on reserve** applying for a **different** unit — scored & ranked; this is the **"On Rez" / transfer** case shown on Match). The `HOW_TO` block in `ai-chat/index.ts` and the `housing_applications` `cols` hint spell this out, including the rule to count On-Rez/transfer applicants via `app_type='transfer_request'` (approved status, `assigned_unit_id is null`, not archived) — **never** from the applicants' self-reported `reserve`/`haveHouse` fields.
- **Module gating** — `ai_assistant` is registered in `CLFN_MODULES` (`_enabled`/`_licensed`), so it auto-surfaces a Settings → Nation → Modules toggle (label "AI Assistant (Chat + Draft Notes)") and is per-nation licensable.
- **Loaded app-wide.** The ✦ AI button is in the shared header (`renderAppHeader`) on every page that loads `housing-init.js`, so `ai-assistant.js` is loaded on **all of them** — `housing.html`, `inspections.html`, `match.html`, `inventory.html`, `tenants.html`, `renos.html`, `contractors.html`, `rfq.html`, `finance.html`. The chat panel is **self-injected** by `_ensureAIPanel()` (idempotent — no-ops where housing.html's static `#ai_chat_panel` already exists), mirroring the TIC / reno-questionnaire self-injecting-modal pattern, with Enter-to-send rebound on the injected input. Adding the assistant to a new page = load `ai-assistant.js`; no markup needed.

### Email Intake module (`mail.html` + `mail-init.js` + `supabase/functions/email-intake` + `cloudflare-email-worker/`)

Columns: `message_id` (unique-index dedupe), `from_email`/`from_name`, `subject`, `body_preview`, `body_path`, `attachments` jsonb, `suggested_match` jsonb, `matched_unit_id`, `filed_paths`, `assigned_by`/`assigned_at`/`assign_notes`.
- **Edge Function `supabase/functions/email-intake/index.ts`** (ASCII-only; deployed with **`--no-verify-jwt`** — it's in that list in `deploy-supabase-functions.yml` alongside `support-login` — because the Cloudflare worker sends no Supabase JWT, only `x-intake-secret`): verifies `x-intake-secret === EMAIL_INTAKE_SECRET`; **sender gate — drops any email whose sender isn't an active `staff` row for this nation** (`ilike` with `likeLit` escaping; From is spoofable so it's a strong spam filter, not absolute auth — the shared secret + triage-first are the real protections); stores the **body as plain text always** (`htmlToText` strip, so staff never open attacker HTML); stores attachments (size-checked before atob, 15 max/8–12MB); computes `suggested_match` (sender→tenant→unit; unit address / tenant name found in subject+body — all `ilike` escaped); dedupes on Message-ID; inserts the row. **No write tools; no JWT.**
- **Cloudflare Email Worker `cloudflare-email-worker/worker.js`** (generic, multi-nation): reads the nation from the recipient's local part (`clfn@fnhub.app` → `clfn`), looks its Supabase project up in the platform registry (`nations_public`, cached 5 min, public anon key embedded), and POSTs to that nation's function. **Fallback:** a non-nation local part (e.g. `files@fnhub.app`) uses the `EMAIL_INTAKE_URL` env var (a configured default project) — that's how the lead nation runs a friendly address. The dashboard-pasteable dependency-free variant is documented in `cloudflare-email-worker/README.md`; the committed `worker.js` uses `postal-mime`.
- **Triage UI (`mail-init.js`):** list with KPIs (Needs filing / Filed / Dismissed) + search + status filter; a **triage modal** shows sender, subject, plain-text preview, attachments (open via `sbGetSignedUrl`, behind an **"unverified external file — scan first"** confirm), and suggested matches; **assign** files attachments + body to the unit via `sbSaveFileMeta('tenant', unitId, …)` **reusing the stored objects** (no re-upload — same one-object-many-entities pattern as `fileContractPdf`; the DocLibrary lists by entity meta, not storage path, so files under `email-intake/<id>/…` still surface on the unit's Documents), then PATCHes the row `assigned` + audits (`email_filed`/`email_dismissed`). The **"Forwarded by \<employee\>"** column resolves the sender against the `staff` table (`_mailLoadStaff`/`_mailForwardedBy`).
- **Per-nation config:** the forward-to address is a per-nation `intake_email` in **Settings → Nation → "Email Intake Address"** (default `<nation-id>@fnhub.app` via `window.nationIntakeEmail()`), shown as a banner on the Email Intake page; plumbed through `shared-config.js` + `applyNationOverrides` (shared-ui.js) like `finance_email`. **The admin control panel** (`admin/admin.js`) has a per-nation **"Email Intake" tab** on the Nation card with the full setup checklist (migration, secret, Cloudflare rule, app address, test) — the canonical onboarding steps; keep it in sync when the setup changes.
- **Onboarding a new nation:** run the migration (fleet), set `EMAIL_INTAKE_SECRET` (the **same shared value** on every nation's project + the Cloudflare worker), add a Cloudflare routing rule `pattern = <subdomain>` → the worker, set its `intake_email` in Settings. **Never** enable Email Routing on a nation's own M365/Google mail domain (it hijacks the MX). No app code changes.

## Conventions

- **Vanilla JS only.** No bundler, no transpiler, no JSX, no TypeScript. Use ES5-compatible patterns (`var` is fine and matches existing code; arrow functions and `async/await` are used where they already appear).
- **No new top-level HTML files without a route.** The Cloudflare static-assets Worker serves the repo root as-is, so a new `*.html` file at the root is reachable by its own path automatically — just make sure it is **not** excluded by `.assetsignore`. (Navigation across the app is explicit `window.location.href` to `*.html`, so there is no SPA rewrite to register.)
### Offline / PWA (Phase O1, `sw.js` + `manifest.json`)
A **service worker** (`sw.js`, registered from `shared.js` so it runs on every page incl. `index.html`) makes the app open and **generate/sign forms with no internet**. Strategy: **network-first** for our own files (always fresh online, cached copy offline — there's no build/cache-busting, so network-first avoids serving stale code to online users), **cache-first** for the immutable CDN libs (jsPDF, jspdf-autotable, Chart.js — so PDF/chart generation works offline), and **Supabase REST/Storage/Auth/Functions is never cached** (pass-through; the app's own degraded-mode save-queue handles offline data). Install pre-caches the boot shell (`index.html` + the `shared.*` layer) + those libs; other pages cache on first (online) visit, so a device must open the app **online once** to populate the cache. `manifest.json` is intentionally generic (no hardcoded nation name) and injected via `shared.js`. **Bump `CACHE` in `sw.js` only if you need to force every client to drop the old cache** (network-first means routine deploys don't require it). **Offline file save (Phase O2):** `uploadFileResilient(path, blob, meta)` + `flushOfflineFiles()` in `shared.js` — an IndexedDB queue (`clfn_offline_files`) that stashes the PDF blob + the `file_uploaded` audit metadata when offline/degraded/on-failure and flushes on the `online` event, on load, and on degraded-mode recovery. It's a drop-in for the `sbUploadFile` + `sbSaveFileMeta` pair; wired into the TIC lease/agreement generator. To make any other uploader (DocLibrary, work order, inspections) offline-safe, swap its `sbUploadFile`+`sbSaveFileMeta` for `uploadFileResilient`.

- **External CDNs are CSP-allowlisted, not bundled.** The few third-party libs (jsPDF, Chart.js, Leaflet 1.9.4, exifr) load from `cdnjs.cloudflare.com` / `cdn.jsdelivr.net`, and the TIC Overview map embeds an `openstreetmap.org` iframe. Any new CDN host, connect target, or frame source must be added to the `Content-Security-Policy` header in `_headers` or the browser will block it. **`connect-src` includes `cdnjs.cloudflare.com` + `cdn.jsdelivr.net`** so the browser can fetch lib **source maps** (`.map`) — those go through `connect-src`, not `script-src`, and were throwing console CSP errors before. Prefer lazy-loading heavy libs on first use (as the SLP modal does) over global `<script>` tags.
- **Page layout, tables, pills, forms, and breakpoints are defined in `shared.css`.** Do not duplicate. The full template + class catalog is in `CLFN_PAGE_TEMPLATE.md` — read it before adding a new view. New view IDs must be added to the `shared.css` padding-top list and `housing.css` responsive overrides.
- **Helper functions called from dynamic renders must live in `shared-data.js`** (not scoped inside page-level functions) so both `housing.html` and `renos.html` can call them.
- **Canonical single-source helpers — do not re-implement locally:** `window.normNameKey(s)` (shared-data.js) is the name-equality normalizer every name-keyed feature (Correct Name, A/R import matching, joint-account warning, policy prior-allocation) must resolve through; `window.policyAgeYears(dob)` (policy-rules.js) is the age-from-DOB calc (TIC `_ticAgeNum` and the council dashboard delegate to it); `window.INCOME_TYPES` / `window.INCOME_TYPE_CANON` (shared-config.js) are the income-type option list + legacy-label migration map consumed by the portal (apply.js), the TIC, and any new option list; `window.formatCurrency` and `window.loadJsPdf({autotable:true})` (shared.js) remain the money formatter and PDF loader — several local copies of each were removed in the C-audit pass, don't re-add them.
- **Edge functions share `_shared/mr.ts`** for maintenance-request plumbing: `decodePhoto`/`uploadMrPhotos` (base64-size-checked BEFORE atob; the `tenants/<unitId>/tenant-mr/<subId>/photo-N.<ext>` path convention staff review depends on), `mrSubject(urgency, address)`, and `resolveStaffRecipients(...)` — both `tenant-mr` and `applicant-intake` import it, so a change there needs BOTH functions redeployed. `_shared/email.ts` also exports `isSafeRedirect` (host-allowlisted auth-link redirects) used by applicant-intake and request-password-reset.
- **Member portal vs application intake are separate switches in behavior:** `external_applications_enabled` OFF refuses `save_draft`/`submit`/`withdraw`/`invite`, but `ping` still answers (flagged `portal_disabled` — apply.js shows the closed notice in the applications card only) and `report_mr` still files, so closing application intake never kills housed members' My Home card or maintenance reporting.
- **No `@supabase/supabase-js`** — all Supabase calls are raw `fetch()` to REST/Auth/Storage endpoints (see `shared.js:941`). The `window._sb = null` lines in `housing-init.js`, `contractors.html`, and `renos.html` are dead code — the SDK is never loaded so `_sb` stays null forever. The actual session access token lives at `HOUSING_SESSION.accessToken`. Don't reference `_sb`.
- **Refactor moves to `shared.js` are deferred to Phase C** (`PLAN.md`). Don't preemptively hoist things; snapshot files first as documented.
- **`finance.html` is ~124 KB** (the old ~12 MB inline base64 logo was removed — the logo now comes from the shared theme like every page). The finance module's logic lives in ~22 `finance-*.js` files (~9.8k lines), not inline in the HTML. It loads `shared.css` + the shared layer and applies the nation theme; `finance.css` is fully token-driven (`var(--…)`). Remaining off-theme bits are hardcoded inline-style colors in some `finance-*.js` renderers — tokenize screen-facing ones, but leave literal hex in the jsPDF/print generators (jsPDF can't parse `var()`).
- **`input[type="date"]` fields are normalized app-wide** (`shared.css`, loaded by every page). Raw date inputs have three iOS Safari quirks otherwise: an empty one renders as a totally blank box (no calendar icon, no `mm/dd/yyyy` placeholder like the selects beside it); a filled one renders taller than an empty one so the field jumps in height once a date is picked; and `-webkit-appearance: none` (needed to fix the first two) strips iOS's own comfortable minimum touch height, so the field then renders visibly *shorter* than the untouched text/select inputs beside it. The fix sets an explicit `line-height`/`min-height` (matching `.f input`/`.f select`'s computed box height, ~43px) plus a background-image calendar icon; `::-webkit-calendar-picker-indicator` is stretched invisibly over the field so Chrome's native picker still opens on tap anywhere in the box. This is a single global rule — don't add a per-page or per-modal override unless a specific field genuinely needs different sizing, and don't drop the explicit height thinking padding alone will keep it in sync with sibling fields.
- **`-webkit-text-size-adjust: 100%` on `html`** (`shared.css` Base Reset) disables iOS Safari's automatic text-autosizing/font-boosting. Without it, a short `<label>` sitting in a wide grid column next to a much narrower sibling column — e.g. the Edit Unit / TIC address row's `Number` (80px column) / `Street` (1fr column) pair — gets silently inflated by WebKit's readability heuristic well past its CSS `font-size`, differently between portrait and landscape, and visually bleeds into whatever sits above it in the layout (looked like a giant clipped word overlapping the tab bar). If a label ever looks mysteriously oversized only on a phone and only in a narrow/wide column pair, this is the mechanism — don't chase it as a flexbox/grid bug.

### Buttons & Export dropdowns (shared design — do not re-derive)

Always pair `.btn` (the size/family base) with one variant. Don't mix the `.btn-*` family with the legacy `.btn-header-ghost` (page-top header only) — their padding and font-size differ and the buttons will look mismatched side-by-side.

| Class                         | Surface                | Visual                                      | Use for                              |
| ----------------------------- | ---------------------- | ------------------------------------------- | ------------------------------------ |
| `.btn .btn-primary`           | any                    | yellow fill, dark text                      | the primary action in a row          |
| `.btn .btn-ghost`             | light cards            | transparent, text-coloured border           | secondary on light surfaces          |
| `.btn .btn-ghost-dark`        | dark `.modal-hdr`      | transparent until hover (rgba white tint)   | secondary on dark card headers       |
| `.btn-header-ghost`           | page-top dark header   | grey border, yellow on hover                | only the top header strip            |

Multiple buttons in a `.modal-hdr` use the existing flex row — don't invent a new wrapper:
```
<div class="flex-gap8 flex-wrap">
  <button class="btn btn-ghost-dark">Secondary</button>
  <button class="btn btn-primary">Primary</button>
</div>
```

**Inline Export dropdown.** When a card needs its own Export button (audit log, future panels), reuse the shared `.export-dropdown` wrap with the existing `.header-export-menu` / `.header-export-item` styling. Toggle helper is `toggleExportMenu(this)` in `shared-data.js`. Export logic flows through `_doExport(format, headers, data, filename, colWidths)` — also shared. Page-level Export (Inventory, Match, Renos, Contractors) uses `setExportView(name)` + `headerExport(format)`; don't wire new views into that unless they're top-level page views.

When two action buttons sit side-by-side in a `.modal-hdr`, **both should use `.btn .btn-primary`** (yellow) — mixing primary + ghost reads as visual noise on the dark card header.

Reference markup (audit log, `housing.html` `#sec_audit`):
```
<div class="flex-gap8 flex-wrap">
  <div class="export-dropdown">
    <button onclick="toggleExportMenu(this)" class="btn btn-primary">📤 Export</button>
    <div class="header-export-menu">
      <button onclick="exportAudit('csv')"   class="header-export-item">CSV</button>
      <button onclick="exportAudit('excel')" class="header-export-item">Excel</button>
    </div>
  </div>
  <button onclick="renderAuditLog()" class="btn btn-primary">↻ Refresh</button>
</div>
```
